## 1. Decisions

- **Prompt:** Respond to the [Node.js October 2026 security releases](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) (4 High CVEs, including TLS hostname-verification bypasses CVE-2026-105483 and CVE-2026-106069 and a Brotli out-of-bounds write CVE-2026-111497; fixed in 26.12.1, 24.22.1, and 22.23.4).
- **Goal:** Every release job that runs `npm` runs the newest Node 24.x, which is 24.22.1 or later today, and a repo test stops a future job from running `npm` on an unpinned Node.
- **Scope:** `.github/workflows/release.yml` jobs `npm` and `channels`, and `test/repo.test.ts` · **Non-goals:** the `so` binary and CI test jobs (they run on Bun, not Node); bumping Bun; tagging or publishing a release.
- **UI:** `not needed — CI workflow and repo test only`

Only the release workflow runs Node. The app is built and run by Bun, so the advisory does not reach the shipped binary:

```text
so binary      ── bun build --compile ──► Bun runtime            not affected
ci.yml         ── setup-bun ──► bun test / build                 not affected
release.yml    npm job      ── setup-node "24" (toolcache) ──► npm publish --provenance   affected
               channels job ── macos-15 image's Node ──► npm publish --dry-run, npm install -g   affected
```

### Q&A Log

| Q | Question | Answer | Decides |
|---|---|---|---|
| `A1` | Is the `so` binary affected? | No. It is compiled and run by Bun 1.4.2 — `package.json` `"packageManager": "bun@1.4.2"`, `build` script `bun build --compile`; Bun has its own `node:*` modules | Scope |
| `A2` | Which jobs run Node? | `npm` (`setup-node` `node-version: "24"`) — `.github/workflows/release.yml:124`; `channels` runs `npm` from the `macos-15` image's preinstalled Node with no `setup-node` — `.github/workflows/release.yml:86-89` | `REQ1` |
| `A3` | How to get the patched Node? | `check-latest: true` on `setup-node`: without it the action uses the runner toolcache's 24.x when one is cached, which can predate 24.22.1 (setup-node `docs/advanced-usage.md`, "Check latest version"). The setup-node manifest (`actions/node-versions`) already lists 24.22.1 (checked 2026-10-22). Tracking the line beats an exact `24.22.1` pin: Dependabot does not bump `node-version`, so an exact pin would miss the next security release | `DES1`, `DES2` |
| `A4` | Should `channels` get its own `setup-node`? | Yes. It runs `npm publish --dry-run` against registry.npmjs.org and `npm install -g`, so it needs the same patched Node; the image's Node version is outside our control | `DES2` |
| `A5` | How to stop a regression? | Add a test to `test/repo.test.ts`, which already enforces workflow pins (`test/repo.test.ts:31`) | `REQ2`, `DES3` |
| `A6` | How to prove the workflow still works? | `actionlint` locally, the `zizmor` job on the PR, and one non-publishing release dry run (`gh workflow run release.yml`), which runs `channels`; the `npm` job runs only on a tag, so the repo test and `actionlint` cover it | `V2`, `V3` |

No questions — every decision follows from the prompt and the code.

#### Test Strategy

- **Prioritize:** a job running `npm` on an old or unpinned Node (`V1`), a malformed workflow (`V2`), and `channels` still installing the npm packages on the new Node (`V3`).
- **Skip:** setup-node's own resolution logic (library behavior, documented in `A3`).
- **Prove once:** `V1` guards the shape; `V3` runs it once for real.
