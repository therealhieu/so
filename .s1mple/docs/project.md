## Purpose and Scope

`so` is a terminal editor for a folder of Markdown notes, run as `so [path]`. It is one Bun process with a pure TypeScript core: a language-neutral editor kernel (text, vim, commands, view) plus registered file types, driven by one-way state flow, thin I/O adapters, and an OpenTUI shell that draws only visible lines. A worker thread scans the workspace into a link index (NoteIndex), so links, backlinks, link-safe renames, pickers, and search work without blocking typing. Markdown notes open in a read-only `reading` view by default, and `<leader>m` cycles to an Obsidian-style `live` view (rendered blocks, with source shown on the cursor's lines) and a `source` view; a note opened to write in (a new note or a daily note) opens in `live`; images, note embeds, math, and Mermaid draw in the terminal. On a terminal that sizes text (kitty's OSC 66, which OpenTUI's startup probe reports as `capabilities.scaled_text`), H1 headings draw at 1.75×, H2 at 1.6×, and H3 at 1.4× (two rows per wrapped row), and math scripts and footnote labels draw half size, two to a cell; `preview.sizedText` (default on) turns it off, and elsewhere (herdr 0.9.5 included) everything draws as before. A table wider than the window wraps its cells to fit (header words too), and shows each row as `Header: value` records when a column would get fewer than 8 cells (`src/core/lang/markdown/renderers/table.ts`). A note's window caps its text at `preview.readableWidth` columns (default 100) and centers it with the gutter while `preview.readable` is on (default off; `<leader>ur` toggles it), and `preview.justify` (default off; `<leader>uj`) spreads the wrapped rows of paragraphs and list items to both edges in the `reading` and `live` views, except the last row of a line and revealed source. `:Preview` mirrors the active note in a read-only browser page served on `127.0.0.1`. Daily notes (`:Today`, `:Yesterday`, `:Tomorrow`, a calendar picker) and templates are created from Obsidian-compatible templates and never overwrite a file; Obsidian `.base` files open as read-only table and Kanban views whose cell edits and card moves write one frontmatter key back to the note, and `![[x.base#View]]` embeds render inline. PDFs open in a read-only window that draws one page at a time in the terminal, fit to the width (scrolling a taller page) or whole, with `j`/`k`, `J`/`K`, `gg`/`G`, `:Page N`, and the wheel, text search (`/`, `?`, `n`/`N`, by page), mouse text selection on the page (drag, double-click a word, triple-click a line; `y` copies, `<Esc>` clears), an action float under a selection when the button comes up (or on `ga`) with Highlight (`h`), Note (`n`, typed in a prompt), and Copy (`y`), and on a clicked highlight or note Delete (`d`) and Copy, plus Edit (`e`) on a note, highlights and notes tinted on the page and a note's text floating while the pointer rests on it, kept per PDF in `.so/annotations/<pdf path>.json` and moved with the PDF on an explorer rename, and a `<leader>p` group holding every other PDF tool: the highlights and notes picker (`pa`; the active PDF's highlights and notes in reading order, detached ones last, opened at the first one on or after the shown page; typing filters the quote and note; Enter shows the page scrolled to it; `C-e` edits a note or adds one to a highlight, `C-y` copies the quote, `C-x` deletes; at 100 columns and up a pane shows the page, the whole quote, and the whole note), a contents picker (`po`), go to page (`pg`), zoom in the window (`pz` for 2×, also `+`/`-`/`0`, `h`/`l` to pan), a dark page in the theme's colours (`pi`), and a copied page link (`py`), and `![[x.pdf#page=N]]` embeds draw that page inline; pages, text, and contents come from Poppler (`pdftoppm`, `pdfinfo`, `pdftotext`, `pdftohtml`) found on `PATH`, and without it a PDF still opens with an install hint and `:Open` shows it in the system viewer. SQLite databases (`.db`, `.sqlite`, `.sqlite3`, `.db3`) open in a read-only window: a table or view at a time in a paged grid (the first table, or the one a `#name` subpath names; `t` picks another), its schema (`Tab`), one value whole (`Enter`: JSON indented, a BLOB as a hex dump), `y` to copy a value, `R` to read the file again, and `s` for a query dialog (one read-only statement, checked while typing, `Tab` completing table and column names, `↑`/`↓` for past queries) whose rows replace the grid until `Esc`; a `.db` file without SQLite's header says so. HTML files (`.html`, `.htm`) open in a browser window: a headless Chrome on the machine running `so` draws the page, and its frames show in the terminal as images, so it works over SSH too; the mouse always goes to the page, Normal mode keeps `j`/`k`/`<C-d>`/`<C-u>` (scroll), `gg`/`G`, `H`/`L` (back and forward), `r` (reload), `+`/`-`/`0` (zoom), and `y` (copy the page's selection), `i` (or a click into a text field) enters BROWSE mode, where every key goes to the page until `<C-\><C-n>`, and `<leader>m` flips the window to its editable source and back; a save shows the page again, and without Chrome the window says what to install. Pictures (`.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`) open in a read-only image window fitted to it, with `+`/`=`/`-` and the wheel to zoom (0.25× to 8×), `0` to fit, `hjkl`/arrows and a drag to pan, and the size and zoom in the statusline; `.svg` files open drawn in the same window, and `<leader>m` flips to their editable XML source and back. Videos (`.mp4`, `.m4v`, `.mov`, `.webm`, `.mkv`, `.avi`) open in a read-only video window: a still frame over a row of what the video holds and a timeline, `h`/`l` a tenth of the video, `H`/`L` and the wheel a hundredth, `gg`/`G` either end, and `Enter` or `o` playing it in the system player (`:Open`); frames and facts come from `ffmpeg` and `ffprobe` on `PATH`, and without them the window says what to install. The mouse (wheel, click, double- and triple-click, drag, Ctrl+click) works on every TUI surface and always runs the same path as a keyboard action, and a pointer resting on a word in a code file hovers it like `K`; the `mouse` setting turns terminal mouse reporting off. Inside a Git repository (Git ≥ 2.31), a change column beside the line numbers marks lines that differ from the index, the statusline shows the branch, operation, and change counts, the explorer marks changed files, hunks can be previewed, staged, reset, and jumped between, the cursor line can be blamed, and `<leader>gg` hands the terminal to a configured tool (default lazygit); outside a repository, or without a usable Git, every surface is the same as without the feature. Code files get language-server features unless `[lsp] enabled = false` turns them off (default on); a request no server answers says why (off, none configured for the file type, or each server's binary or crash state): diagnostics as gutter signs, underlines, and the message after the line, inlay hints drawn between characters, highlighted uses of the symbol under the cursor, hover and signature floats, go-to (definition, declaration, type definition, implementation), reference and workspace-symbol pickers, rename and code actions through one workspace-edit path, formatting (optionally on save), and code completion; one process runs per server and project root, servers are found on `PATH` (the TypeScript and JSON servers first in the root's `node_modules/.bin`), and every server stops when `so` exits. Opening a code file directly (`so src/main.rs`) makes its nearest `.git` folder the workspace when a server serves its file type, so the server sees the whole project. ## Architecture and Key Flows

```text
key → src/ui (normalize) → store.dispatch(action) → core update(state, action) → { state, effects }
                                                                                    │
                     src/ui repaints visible lines ◄── state        effects ──► src/app effect runner
                                                                                    │
                                              result actions ◄── src/workspace (fs, trash, clipboard)
```

Mouse input enters through one full-screen, paint-free `MouseLayer` and one router (`src/ui/mouse.ts`); views translate a cell into a model-level `MouseTarget` from the geometry of their last layout, and the pure `onMouse` reducer (`src/core/state/mouse.ts`) replays the matching keyboard path:

```text
SGR mouse (any-motion tracking) → MouseLayer → router: drop when off / right / middle button; a move only when its target changes; Shift turns a vertical wheel notch sideways
   → first source in z-order with a target (overlays → toasts (wheel only) → cmdline popup and message → statusline → side panel → explorer → bufferline → windows)
   → click count (same cell ≤ 500 ms) · drag capture to the press window
   → store.dispatch({type:"mouse", event, now}) → onMouse: overlay gate → focus → keys / commands / exported reducers
```

A move with no button held reaches `onMouse` before the overlay gate: resting 500 ms (timer `lspPointer`) on a word of the active window's code buffer, in Normal mode with no overlay open, sends an automatic hover marked `pointer`. That float hangs under the pointer (the router keeps its last cell), stays while the pointer is on it, and closes when the pointer leaves the word; an answer that arrives after the pointer left shows nothing, and a float opened with `K` is not closed by the pointer.

A rendered span can carry `fold` (a block id); the text view reports a press on it as the `fold` window spot, and `onMouse` flips that block's fold in the window like `za`, without moving the cursor. Callouts with `+`/`-` tag their `▸`/`▾` marker this way. A repeated click on one cell keeps the first click's target, because that click can reveal source and move the text under the pointer. A double click on a tag (inline, or a frontmatter chip, whose span carries `tag`) opens the `tagNotes` picker instead of selecting the word; `gd` (`link.followOrTag`) does the same when there is no link under the cursor.

`update` is pure and synchronous; adapters only execute effects and report results as actions. Saves are atomic (private `0600` temp file, fsync, rename) and keep mode, BOM, line endings, and the trailing newline; the watcher ignores the app's own operations.

Startup reads `config.toml` and the state file synchronously, paints the first frame, and only then starts the watcher and the index worker (`setImmediate` in `src/app/main.ts`), so the first frame does not depend on the workspace size:

```text
src/workspace/index-worker.ts ──batch{summaries, done, total, removed?}*──► src/app/index-host.ts ──indexBatch──► store
          ▲ scan / changed / removed / search                       one crash restarts; a second → "index unavailable"
          └──────────── watcher events and the app's own saves ──────┘
```

The worker reads notes and never writes; only the runner's serial queue writes files. The index lives in memory and is rebuilt at every start.

Live preview is a decoration provider over the kernel's `layoutText`: the Markdown view's `input` hook builds `MarkdownViewInput` (the `Doc`, the view, and a `PreviewCtx` from `src/core/state/view-context.ts`), and `livePreview` renders only blocks in the viewport through the `registerBlockRenderer` registry. Embed targets load as unlisted buffers (never shown, listed, or persisted); decoded images live only in the UI's 64 MiB cache.

On a kitty terminal (with an `imageScaler`, which `main.ts` always passes), note pictures skip that cache and go through `NotePictures` (`src/ui/note-pictures.ts`), so a wheel scroll past a page of photos never decodes on the main thread or uploads a picture twice. A picture's size comes from its file header (`pictureSize` in `src/ui/picture-size.ts`: PNG, JPEG turned by its EXIF orientation, GIF, WebP; tested against OpenTUI's decoder), else from the scale worker; the worker (`src/ui/image-scale-worker.ts`, behind `createImageScaler` in `src/ui/image-scaler.ts`) decodes and makes the copy the terminal gets, scaled down (never up) to the box the picture shows in and PNG-encoded, one request at a time and the newest waiting first, so what is on screen is made before what was scrolled past. Files and copies stay within 64 MiB, least recently used first out; the previous copy shows while one for a new box is made, and a picture not ready yet shows `◌ name`. `ImageSlots` (`src/ui/image-slots.ts`), a renderable drawn after the windows, gives each picture a fixed place among the frame's kitty images, because OpenTUI names a kitty image by its draw order and uploads it again when that place shows another image: a picture scrolled away is drawn as one cell on the statusline's first cell (which the statusline paints over), so it stays uploaded, within 64 MiB of terminal pixels; a place freed holds a transparent pixel. Under herdr a picture not yet uploaded is sent only after it has been drawn in every frame for 120 ms (`HERDR_PICTURE_SETTLE_MS`), because herdr 0.9.5 passes every picture on to Ghostty inline as raw pixels (its file path stops after the first image whose layout changes in flight) and resends it whenever the window cuts it differently, about 10 MB each. The `pictures` sandbox profile stages a gallery note of 30 pictures for checking this by hand.

Sized text (kitty's text sizing protocol, OSC 66) works like note pictures because OpenTUI knows only one-row cells. `PreviewCtx.sizedText` is `ViewHost.sizedText` (the UI's `capabilities.scaled_text`; the shell repaints on OpenTUI's `capabilities` event) and `preview.sizedText`. The heading renderer then replaces an H1–H3 (ATX or setext) with a `sizedText` block widget, drawn without the level glyph or heading band (the size shows the level), whose `SizedBlock` rows of chunks come from `wrapSized` (`src/core/kernel/view/sized.ts`: a `SizedScale` is `n/d` of double size, 7/8, 4/5, and 7/10; a same-style run is cut every `d / gcd(n, d)` cells, which fill exactly `n / gcd(n, d)` double cells (at most kitty's 7), and a chunk of `w` cells takes `2 × ceil(n × w / d)` columns), two screen rows per row; a revealed heading in `live` view gets blank rows below its source (counted with `editor.wrap` and `tabWidth`) so nothing below moves. Math (`mathRuns`) and footnote labels (`footnoteRef` in `inline.ts`) become `Span.script` pairs: one placeholder cell per two half-size characters, so kernel widths do not change; tables keep Unicode `mathText`, and note embeds never size text. `SizedText` (`src/ui/sized-text.ts`) collects the frame's draws from the painter and `paintLine`; a renderer post-process step skips a draw something painted over, erases with `ECH` every row of each old sized area about to be rewritten (kitty otherwise pushes OSC 66 glyphs written into an erased block's lower row past it) through OpenTUI's private `writeOut`, which queues before the frame, and marks those areas changed in `currentRenderBuffer`; on the `frame` event the draws that are new, moved, written over, or after a resize, resume, or forced full repaint (`forceFullRepaintRequested`) go out in one synchronized write wrapped in `ESC 7`/`ESC 8`.

```text
:Preview → preview = starting → startPreview effect → src/app/preview-host.ts → src/preview/server.ts (127.0.0.1:<port>)
   → previewStarted → openUrl     edit or switch → SSE "doc" → page GET /render → swap and scroll
:PreviewStop | exit → SSE "stopped" → server stops → preview = off
```

The server answers GET only, rejects a foreign `Host`, and answers only a request carrying its random per-server token, so another local user cannot read the workspace through it: the opened address carries the token in its query, and that response sets it as an `HttpOnly`, `SameSite=Strict` cookie named for the port (`so-preview-<port>`), which the page's own requests send. It serves workspace files under `/file/*` with containment and a sandboxing policy, and the page loads nothing outside its own origin.

Language servers follow the same one-way flow. The core holds `LspState` and emits `lsp` effects; the host observes the store to start servers and sync documents, and answers with actions:

```text
store change → lspHost.observe: attach (spec by file type, root by markers) → spawn or reuse client → didOpen / didChange (150 ms debounce) / didClose
key (K, gd, grn, …) → core request → lsp effect → runner → lspHost.run → client request → lspResult → float, jump, picker, or workspace edit
server → publishDiagnostics | $/progress | showMessage → lspDiagnostics | lspServer (100 ms throttle) | lspMessage → state → views
didOpen / didChange / workspace/inlayHint/refresh → lspHost: textDocument/inlayHint → lspInlayHints → state → views
cursor rests 250 ms (Normal) → lspHighlight timer → documentHighlight request → highlights → views
exit → lspHost.stop(): shutdown → exit → SIGKILL survivors at 500 ms; resolves only after every server and version probe has exited
```

A crash restarts the server and resends open documents; the fifth crash within 3 minutes leaves it `failed`. A server that exits before `initialize` completes is `unavailable` and stays silent; a missing binary is `missing`; both show only in `:LspInfo`, which lists every wanted server with its state and, once started, the binary it runs from (`ServerView.binary`, e.g. a project's own `node_modules/.bin/tsc`).

Notes are created only through the `createNote` effect, whose adapter expands the template and calls `createExclusive` (temp file + `link()`, `wx` fallback), so an existing path is never replaced:

```text
:Today | calendar Enter | <leader>nn → note-commands → (index hit) openPath{after} | createNote effect
   → runner (serial): read template → expandTemplate → createExclusive → noteCreated → open, cursor on first unchecked task
```

`.base` files are file type and editor kind `base` by registration only (`src/core/features/bases/file-type.ts`): the buffer is `readOnly` (the save gate refuses it), keys never reach vim, and `EditorKindSpec.open` creates the window's `kindState`. `baseViewModel` (`src/core/state/base-model.ts`) derives the table or board from the index's candidates and memoizes it. A table column's width (`TableColumn.width`, cells) is the window's resized width, else the view's `columnSize` (Obsidian pixels ÷ 8; keys with or without `note.`), else its widest header or cell up to 24, never under 3; `>`/`<` widen or narrow the focused column by 4, `=` returns it, and a drag on a header separator (the `baseEdge` window spot) resizes the column to its left, a double click returning it. `layoutBaseTable` (`src/ui/widgets/base.ts`) shows every column when they fit; otherwise the first column stays pinned (at most half the width), the columns after it start `BaseWindowState.scroll.col` columns in (moved so the focused column shows whole), the next column is drawn clipped when 6 or more cells are left (it has no resize edge, and focusing it scrolls it in), and the header shows `‹ +N` after the pinned column and `+N cols ›` at the right edge; `BaseView` reports the columns it shows scrolled off (the `baseScrolled` action, after the frame and only when it differs, like `zoomFill`), so `scroll.col` follows focus moves; `H`/`L` (and a sideways or Shift wheel notch) scroll the columns after the pinned one, taking the focus along unless it is on the pinned column, and the hint shows `H/L scroll` while columns are hidden. `o` (`base.newRow`) asks for a new note's name in a "New row" prompt prefilled with the folder the filters ask for (`newNoteSeed`, `src/core/features/bases/new-note.ts`: the first `file.inFolder`, else the base's folder), and Enter creates it blank (no template picker) through `createNote` with `frontmatter` and `reason: "row"`: the properties the filters in effect require (`file.hasTag`, `file.hasProperty`, `property == literal` in `and` lists and `&&` chains; `or`, `not`, and other comparisons add nothing), the window's pins, and the focused group or lane; then the view's other note-property columns, empty (`[]` for list types), with a `created_at` column (by name, or base type `created_at`/`created_time`) set to the local `YYYY-MM-DDTHH:mm:ss` of Enter and an `updated_at` column (or `last_edited` type) left out so it shows the file's modified time; all set by `seedFrontmatter` over the template text so they win; the answer carries the written text, which the index takes at once, and the base window focuses the new row (`focus.path`) instead of opening the note. Date cells (`src/core/features/bases/dates.ts`) show as local `YYYY-MM-DD HH:mm:ss` however they are written (file times; `T` or a space; with or without seconds, fraction, `Z`, or offset; no zone means local time), a date alone as `YYYY-MM-DD`, and sort and summarize by instant; a note without `created_at`/`updated_at` shows its file's ctime/mtime there. Resized widths live only in the window state (`BaseWindowState.widths`), are dropped when the view changes, and never reach the file; likewise `/` filters rows by text (rows with a cell containing it, ignoring case) and `F` pins the focused cell's value (stacking across properties; `c` clears both): `BaseWindowState.query` and `pins` reach the evaluator as `BaseUi`, apply after the base and view filters and before `limit`, and are dropped when the view changes; embeds use `columnSize` and content widths. A cell edit or card move writes one frontmatter key:

```text
open note   → applyBufferEdits (one undo step)
closed note → patchFrontmatter effect (serial queue) → read → refuse if stale → patch → atomic write → frontmatterPatched
```

Git starts after the first frame. Every Git call runs through `src/workspace/git.ts` as an argv (never a shell) with `--no-optional-locks` and `--literal-pathspecs`, with patch and buffer contents only on stdin; its output is decoded keeping a leading BOM, so index text compares with the buffer exactly. The core only sees results:

```text
first frame → detect (git missing → inert; < 2.31 → warn notice, inert; no repo → inert)
   → gitDetected → watch the git dirs → status (coalesced 200 ms) → index read per open file whose status entry changed
     (every open tracked file after a git-dir change, e.g. an outside checkout)
   → buffer edit → 100 ms diff timer → hunks → change column, statusline counts, explorer markers
<leader>ghs / <leader>gg → save gate (unsaved buffers are written first; a failed save stops) → stage patch | tool hand-off
tool hand-off → flush frame → hold interrupts → suspend shell → tool runs → reset foreign modes → resume → re-read buffers, status, and index
```

`![[x.base#View]]` loads the base as an unlisted embed buffer because its file type has an embed model (`EmbedModelRegistry`), and the `base` block renderer reads `PreviewCtx.embedModel`. Kanban stays behind `KANBAN_TYPE` (`src/core/features/bases/types.ts`), which is `undefined` until an Obsidian-saved Kanban `.base` fixture confirms the layout's `type`; until then, `kanban` views fall back to a table with a notice.


PDFs are file type and editor kind `pdf` (`src/core/features/pdf/file-type.ts`), a `binary` file type: the runner reads such a path with `readBinaryFile` (an empty body stamped like its bytes, so disk changes still reload) instead of `readTextFile`, which would refuse it; the buffer is `readOnly` and `binary`, and git never diffs it. `syncPdfInfo` (`src/core/state/pdf.ts`) asks for the page count (`pdfInfo` effect) once per file stamp and drops stale answers; `PdfWindowState` holds the page, the fit (`width`/`page`), and the rows scrolled, plus the layout `PdfView` (`src/ui/editors/pdf-view.ts`) reports after a frame (`pdfLaidOut`, like `baseScrolled`), so `j`/`k` cross pages. `src/workspace/pdf.ts` runs Poppler as an argv on the workspace-contained real path, at most two at once, with timeouts and output caps; on macOS it runs with `FONTCONFIG_FILE` set to a config `so` writes under `$XDG_CACHE_HOME/so` (`~/.cache/so`; `popplerEnv`: the system and user font folders only), because Homebrew's stock fontconfig rules resolve Helvetica, the font PDFs most often leave out, to Hiragino Sans, which Poppler draws as blank text; pages come as raw PPM (Poppler's PNG encoding took about three quarters of a page's time) converted to RGBA at a width snapped to 64 px, cached in `ImageCache` under the file stamp, page, and width; once a page is up the view draws the next one, and with kitty it PNG-encodes the shown page before its first send and the next page shortly after, because OpenTUI's own encoding at send time is fast but about 15 times larger. Text (`pdftotext`, pages split at form feeds) and contents (`pdftohtml -xml`, its `<outline>`) load on first use into `BufferState.pdfText`/`pdfOutline` per file stamp (`src/core/state/pdf-tools.ts`); search is plain text (smartcase, whitespace runs match line breaks) and moves by page, because plain `pdftotext` gives no word positions; the contents picker refreshes when they arrive. Selection reads one page's words and boxes with `pdftotext -bbox-layout -f N -l N` as soon as the active window shows that page (`syncPdfLayout`, so the first press does not wait on Poppler; `BufferState.pdfLayout`, per page and file stamp; `src/core/state/pdf-select.ts`, parsed by `src/core/features/pdf/layout.ts`), because a whole book's `-bbox-layout` output can pass the text cap. `PdfView` maps a cell to a point on the page as fractions of its width and height through the placement it drew (`WindowSpot` `pdf` `at`, absent off the page), and `PdfWindowState.select` keeps the anchor and head as points, so a drag before the words arrive still resolves; a drag selects characters in Poppler's reading order (Poppler gives only word boxes, so each word's width is shared out by its characters' Helvetica widths, close for most fonts and finer than a cell; a monospaced or condensed font can be off by part of a character in long words), a double click whole words, a triple click whole lines, ends when the page changes, and `y` copies it (register and clipboard, like `<leader>py`) because the mouse model has no release event. The page stays the cached image, drawn whole: the rows of cells the selection covers draw over it as tinted copies in blocks of four rows, each kept while its rows and selected text stay the same, so a drag step re-encodes only the block under the pointer (about 3 ms instead of 57 ms for a whole 2048 px page) whatever the selection's height. The page draws first because OpenTUI keys kitty images by draw order and stacks later ones higher: it keeps its slot, so a selection never sends it again. Zoom stays in the PDF window: `PdfWindowState.zoom` (fit width, up to 4×) draws the page that many times the window's width, cropped at `pan` columns, and zooming keeps the window's centre in place; the raster width is still capped at 2048 px, so a large zoom on a wide window enlarges pixels. The dark page recolours the decoded page by lightness into the theme's text colours, cached under its own key. A wheel gesture (events under 250 ms apart) turns at most one page, because terminals send several events per notch. Leaving a buffer saves its editor kind state in the window's `views`, so a PDF or base comes back as it was left.
SQLite databases are file type and editor kind `sqlite` (`src/core/features/sqlite/file-type.ts`), the other `binary` file type, read by `bun:sqlite` in a second worker so no query blocks typing:

```text
open app.db → syncSqlite (src/core/state/sqlite.ts): new stamp or R → BufferState.sqlite loading, gen + 1 → sqliteSchema effect
  → SqliteHost (src/app/sqlite-host.ts): one request at a time, workspace-contained real path, 10 s timeout (terminate, answer failed, respawn)
  → src/workspace/sqlite-worker.ts → src/workspace/sqlite.ts: header check, read-only connection with query_only, closed after each request
  → sqliteSchema action (dropped unless gen and stamp match) → a window without a source takes its start table or the first one
  → syncSqlite: focus outside SqliteWindowState.page → sqlitePage effect (200 rows from offset, one more read for "more"), plus sqliteCount once per table
  → sqlitePage action (kept only when it answers SqliteWindowState.want) → SqliteView: sqliteTableModel → paintBaseTable
```

Pages and counts are tagged with the read's `gen`, so a reload of the same bytes still drops answers to the read before it, and the old rows stay drawn until the new ones come. A page ask replaces one still queued for the same window (it answers `superseded`, which the runner drops). A table reads with `SELECT * … LIMIT 201 OFFSET n`; a query takes one statement (`oneStatement` skips quotes and comments), wraps a `SELECT`/`WITH`/`VALUES` the same way, and runs any other (`PRAGMA`, `EXPLAIN`) whole and cuts it; `readonly` plus `query_only` make every write fail inside SQLite. Cells cross the worker as `SqliteCell` (integers as exact text through `safeIntegers`, text cut at 16 KB with its length, a BLOB's size and first 4 KB as hex), so a message stays small whatever the database holds. Bun uses the system SQLite on macOS and its own on Linux: with a WAL database whose `-wal` and `-shm` files are gone, Linux opens it read-only and creates `-shm` (the database bytes stay as they are), while macOS refuses, so when there is no `-wal` file it opens immutable. `TableCell.dim` lets the shared table painter draw `NULL` (and empty text) dim, so the two stay apart. `SqliteView` reports the columns it scrolled, its body rows, and the lines of the schema or value pane (`sqliteLaidOut`), which `H`/`L`, half-window moves, and pane scrolls follow. The query dialog (overlay `sqliteQuery`, `src/core/state/sqlite-query.ts`, drawn by `SqliteQueryView`) bumps a `gen` on each edit and arms the `sqliteCheck` timer (150 ms); the timer sends the `sqliteCheck` effect, which the worker answers by compiling the statement without running it (`checkStatement`), so a syntax error, an unknown table or column, a statement without result columns, or a parameter fails before `Enter`; only the latest edit's answer is kept, and `Enter` keeps the dialog open while the check says it cannot run. Each window keeps its last 50 queries for `↑`/`↓`. A terminal paste (the `paste` action) goes into the dialog with its line breaks and is dropped elsewhere.

HTML files are file type `html` and editor kind `browser` (`src/core/features/browser/file-type.ts`), not `binary`, so the source stays editable text highlighted as XML. One headless Chrome per `so` process draws every browser window's page, one tab per window:

```text
window drawn → BrowserView: browserLaidOut (device pixels, row height) → syncBrowser (src/core/state/browser.ts): browser effect open | resize | close; a new file stamp opens again
  → BrowserHost (src/app/browser-host.ts): Chrome started for the first page (findChrome, launchChrome), one CDP tab per window, ops in order per window
  → src/workspace/browser: Chrome over --remote-debugging-pipe (fds 3 and 4, NUL-framed JSON), Page.startScreencast as PNG
  → screencast frame → BrowserFrames (src/ui/browser-frames.ts, outside the store) → requestRender → BrowserView draws it, rests, then acks → Chrome sends the next
  → url, title, loading, focus, selection, failures → browserEvent → BrowserWindowState → statusline (WEB / BROWSE, title or loading…, zoom)
key (Normal) → browser.* command → browser effect input (wheel, key) | back | forward | reload | copy
key (BROWSE) → browseKey: every key → input; <C-\> held, <C-n> after it leaves BROWSE, any other key sends both
mouse on the page → WindowSpot browser at (fractions of the frame) → press | drag | release | move | wheel → input; after a release the host asks whether a text field has focus (focus event)
```

Frames stay out of the store because every dispatch repaints every view. The page's CSS viewport is the window's pixels at `pageSize` (one device pixel per CSS pixel per 18 px of row height, 1–3, in quarter steps, divided by the zoom), and Chrome is started with that density (`--force-device-scale-factor`), because a tab's own scale does not reach its screencast. The view keeps pixel copies of what it shows: when a frame differs from them only in bands of rows (`changedBoxes`, `src/ui/browser-patch.ts`) covering under a quarter of the window, only those bands go to the terminal as patch images over the last whole frame (at most 16 before a whole frame replaces them), so a blinking caret or a clock sends a few cells. Chrome keeps about three frames in flight: a frame replaced before it was drawn is acked with the newest (`BrowserFrames.publish`), and after taking a frame the view waits three times as long as taking it took before taking the next, so an always-moving page keeps `so` at most a quarter busy; for 1 s after the host runs any operation but `close` and `copy` (a key, click, wheel, navigation, or resize: `BrowserFrames.drive`), frames are taken without that wait, so scrolling keeps up. The change search (`changedBoxes`) stops as soon as more than a quarter of the cells are known to differ, so a scrolled frame goes whole without being compared to its end. A frame that comes within 300 ms of a wheel step (`BrowserFrames.scroll`, `SCROLLED_MS`) goes whole without any comparison, so its PNG is never decoded: the pixels of what is shown are read from its frame only when the next frame is compared to it, into a buffer the view reuses. A frame with the same bytes as the last one taken is acknowledged without being decoded: Chrome sends one for every wheel step, even a step that moves nothing. Wheel steps that come while one waits in the tab's queue are added to it (`Tab.wheel`), so a trackpad's hundreds of steps a second do not queue behind each other; anything else queued after it starts a new step. herdr 0.9.2 and later (panes with `TERM_PROGRAM=herdr`) hand Ghostty a raw RGBA image within 16 MiB through a file, one image at a time per client, and inline otherwise; when the images' layout (their number or sizes) changes while a file is unconfirmed, herdr 0.9.5 stops using files for that client for good, and every later image goes inline. There `so` keeps the layout fixed: the renderer sends raw images through files (`createRenderer({ imageFiles })`), Chrome scales every frame to at most 2,500,000 pixels from the page's start (`framePixels`, `BrowserPage.limit`: the screencast's `maxWidth`/`maxHeight`, not restarted when the frame already fits), and each frame goes whole, copied out of its PNG so it goes as raw pixels, with no patches (`browserFileRate`). The next frame is taken only once the terminal has written the last and herdr has read its file (`imageFilesPending`, looked at every 2 ms), and a page not driven sends at most 20,000,000 pixels a second. An older herdr passes every new kitty image on as raw pixels and buffers what it cannot send without limit, so there the view also waits until the pixels it sent fit 2,000,000 a second (`browserPixelRate`). Keys go to Chrome with `windowsVirtualKeyCode` and never `nativeVirtualKeyCode`: macOS reads that as its own key code (Home's 36 is Return there), which stops the tab's frames. The title is read again 250 ms after a frame, a release, or a key, because a script sets it without an event. Chrome exits when `so` does, even on `SIGKILL`, because its pipe closes; on a normal exit `stopBrowser` closes the tabs and kills Chrome after 500 ms, and its temporary profile is deleted. With no page open for 30 s Chrome stops, and a crash shows `Chrome stopped` until `r` starts it again.

Pictures are file type `image` and SVG files file type `svg`, both shown by editor kind `image` (`src/core/features/image/file-type.ts`; `.svg` is not in the `xml` code type). `image` is `binary` and `readOnly`; `svg` is text with a `source` view highlighted as XML, flipped like HTML by `flipSource` (`src/core/state/source-view.ts`), and an image window's keys resolve under file type `image` (`keyScope`) so the SVG's source keeps the text keys. `ImageWindowState` is an `ImageFrame` (`src/core/features/image/view.ts`: `level` times the fitted size, the view's centre `cx`/`cy` as fractions of the image, and `fill`, how much of the window the fitted image covers), the zoom float's model shared with it, plus the press a drag pans from and the pixel size the view drew; `ImageView` (`src/ui/editors/image-view.ts`) draws the image `ImageCache` holds under its path with `fitView` (`src/ui/image-fit.ts`, also the zoom float's) and reports `imageLaidOut` after a frame when the fill or size changed. The image loader (`createImageLoader` in `src/workspace/images.ts`) draws a `.svg` path or URL through the resvg rasterizer at its `viewBox` (`svgSize` in `src/core/features/image/svg-size.ts`: `width`/`height` in pixels, else the `viewBox`, else 300×150), its longest side at 2048 pixels within 8 megapixels, on a transparent background, so SVG embeds in notes draw too; resvg's WebAssembly starts once a process. Animated GIFs show their first frame; animated WebP, which neither OpenTUI's decoder nor ffmpeg reads, shows that it could not be drawn.

Videos are file type and editor kind `video` (`src/core/features/video/file-type.ts`), `binary` and `readOnly`. `syncVideoInfo` (`src/core/state/video.ts`) asks for what a video holds (`videoInfo` effect) once per file stamp and drops stale answers into `BufferState.video`; `src/workspace/video.ts` runs `ffprobe -print_format json -show_format -show_streams` (parsed by `parseProbe` in `src/core/features/video/probe.ts`: the first video stream's size after rotation, codec, frame rate, the first audio codec, the length and bytes) and, for a frame, `ffmpeg -ss <at> -i <path> -frames:v 1 -vf scale=<W>:-2 -f image2pipe -vcodec ppm -` (`frameWidth`: even, at most 2048 px), both as an argv on the workspace-contained real path, at most two at once, with timeouts and output caps, through the runner shared with Poppler (`src/workspace/tool-run.ts`). `VideoWindowState` is the moment shown, in seconds, kept between 0 and `lastFrameAt` (a little before the end, where a seek can find no frame); `VideoView` (`src/ui/editors/video-view.ts`) caches each frame under the file stamp, moment, and width, and the last frame stands in while the next draws. Playback is the system player through `openUrl`, because the terminal has no sound and herdr passes images at about 2,000,000 pixels a second.

## Boundaries and Dependencies


## Engineering Standards and Patterns

Keep it lean and simple. Code carries no work-process identifiers (`.s1mple/S1MPLE.md` Implementation).

- **Language Rules:** [TypeScript](languages/typescript.md)
- **Pins:** every npm version is exact; GitHub Actions are pinned to a 40-character commit SHA with a `# <tag>` comment. `test/repo.test.ts` enforces both.

## Constraints

- No version range (`^`, `~`) in `package.json`; upgrades are deliberate PRs.
- No tool may depend on the TypeScript compiler API (TypeScript 7 ships none).
- `src/core` stays free of I/O, runtime, and UI imports.

- **Local Setup:** install Bun `1.4.2`, then `bun install --frozen-lockfile`. - **CI Checks:** `.github/workflows/ci.yml` runs on `pull_request` to `master` only (no `push` trigger), with per-PR concurrency and `cancel-in-progress`. Job `check` (`ubuntu-24.04`) runs `bun run check`; job `test` (matrix `ubuntu-24.04`, `macos-15`) runs `bun run test:ci`, plus `bun run bench` on Linux. The repository is public, so these standard runners cost no Actions minutes.
- **Release:** Nothing is released automatically; a release happens only when the user asks. A pushed `v*` tag runs `release.yml`, which builds four binaries on one runner, smoke-tests each on its native runner (`macos-15`, `macos-15-intel`, `ubuntu-24.04`, `ubuntu-24.04-arm`), and publishes a GitHub Release with generated notes only after every smoke job passes and job `channels` (`macos-15`) has installed the Homebrew formula (from `file://` binaries, after `brew style` and `brew audit`) and the npm packages (`npm publish --dry-run`, then `npm install -g` and `bun add -g` from packed tarballs). After the release, job `npm` publishes the npm packages and job `homebrew` pushes `Formula/so.rb` to `therealhieu/homebrew-tap` once `brew audit --online` and a real install pass. Tags containing `-` publish as prereleases: the npm packages go to dist-tag `next`, and the formula is not updated. A manual run (`gh workflow run release.yml`) is a dry run: the same build, smoke tests, and `channels` checks with version `0.0.0-dev+<short sha>`, nothing published. Phase exits use the dry run.
- **Distribution:** `scripts/release-channels.ts` builds both channels from `dist/so-<target>` and `SHA256SUMS`. Homebrew gets a binary formula `so` in the tap `therealhieu/tap`; Homebrew core's `so` is an unrelated tool. npm (also used by `bun add -g`) gets `@therealhieu/so-<target>` (one binary, `os`/`cpu` set, `libc: glibc` on Linux) for each of the four targets, then `@therealhieu/so`, which lists them as `optionalDependencies` and whose `bin/so` is `scripts/npm-shim.sh`. The shim is POSIX `sh`, so no Node or Bun is needed at run time; it `exec`s the platform binary nested under the package or beside it (hoisted and isolated layouts). npm publishes through trusted publishing (OIDC, `--provenance`); the `NPM_TOKEN` secret is needed only for a package's first publish. Job `homebrew` pushes over SSH with the `HOMEBREW_TAP_DEPLOY_KEY` secret, the private half of a write deploy key on `therealhieu/homebrew-tap` (so it can reach no other repository), checking GitHub's pinned ed25519 host key.
